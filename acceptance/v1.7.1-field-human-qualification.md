## Purpose

This procedure collects the still-missing Human evidence group for three retained V1.7.1 lanes that cannot be honestly reviewed in the browser-only human review surface:

- `touch`
- `alternative-input`
- `native-behavior`

The session must be human-operated on real physical hardware. It may be co-scheduled with the existing Physical-Device or Assistive-Technology qualification session, but the Human evidence record remains separate and does not inherit another evidence type automatically.

## Evidence separation

A Device record is not Human evidence merely because a person operated the device. An Assistive-Technology record is not Human evidence merely because a human operator used the assistive technology. This procedure exists so the human-observation group is independently recorded and reviewable.

Likewise, this Human record does not satisfy Device or Assistive-Technology evidence. Every lane still requires all groups defined by `contracts/v1.7/acceptance.dev.json`.

## Exact-source and session identity

## Common scenarios

Every record must include these observations:

### `source-and-session-identity`

Confirm the source, tooling, integration build, platform, physical device, and operator are concrete and traceable.

### `task-and-focus-continuity`

Perform the lane-specific interaction while observing whether task state, focus, selection, navigation, and recoverable work remain coherent. Record any reset, focus loss, inaccessible state, or unexpected task discontinuity.

### `meaning-and-authority-preservation`

Confirm presentation feedback does not manufacture success, permission, provider truth, security truth, privacy truth, or completion. When source truth is missing or untrusted, observe the fail-closed presentation.

### `accessibility-preference-precedence`

Exercise applicable accessibility settings such as Reduced Motion, Reduced Transparency, Increased Contrast, Forced Colors, large text, or platform input accommodations. Confirm optional richness does not outrank accessibility or task completion.

### `real-human-operation`

Record what the human actually did and perceived. Automation, scripted synthetic clicks, viewport emulation, generated screenshots, or CI output cannot satisfy this scenario.

## Lane-specific scenarios

### Touch — `touch-human-interaction-quality`

Use real touch input on a physical device. Review target reachability, activation confidence, accidental-activation resistance, direct manipulation, interruption/recovery, visible feedback, semantic alternatives, task continuity, and accessibility behavior. The Device evidence group remains independently required.

### Alternative input — `alternative-input-human-interaction-quality`

Use a real assistive or alternative input mode such as switch access, voice access, assistive input, rotary input where applicable, or another concrete non-primary input path. Record the technology name and version when an assistive technology is involved. Review reachability, sequencing, focus/selection behavior, recovery, semantic action equivalence, and task continuity. The Assistive-Technology evidence group remains independently required.

### Native behavior — `native-behavior-human-platform-quality`

Use an actual native implementation on physical hardware. Review platform conventions, native interaction feel, navigation/focus behavior, safe-area/inset behavior, accessibility settings, task continuity, semantic authority, and whether Glaze meaning is preserved without forcing cross-platform mechanical uniformity. The Device evidence group remains independently required.

## Session decision

Use `session-pass` only when every governed scenario in the selected lane record is marked `pass`. Any failed scenario requires `session-fail`.

A session-pass value means only that the candidate Human observation record is internally consistent. It does not mean Human evidence is accepted, the lane is closed, Section 41/48 is accepted, or V1.7.1 is promoted.

## Validation

Run:

```bash
python scripts/validate_glaze_v1_7_1_field_human_qualification.py --record /path/to/candidate.json
```

The validator checks structure, exact-source identity, physical-device/human-operation requirements, lane-specific constraints, scenario completeness, fail-closed authority fields, and placeholder rejection.

The validator does not decide whether the human observations are trustworthy or sufficient. Separate governed review remains required.

## Completion boundary

This control establishes a collection protocol only. CI self-tests, templates, a structurally valid record, or a session-pass value are not accepted Human evidence by themselves. A reviewed durable evidence record must later be governed into the retained qualification working set, and the lane remains incomplete until every other required evidence group is also accepted.

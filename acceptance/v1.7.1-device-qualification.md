# Glaze V1.7.1 — Physical-Device Qualification

**Lifecycle:** V1.7.1 Development qualification control only  
**Current Stable baseline:** Glaze V1.7 / `1.7.0`  
**Frozen source under review:** `4b9d085a5177b96cc31d4270b38d792a59872e37` / `1.7.0-dev.47`  
**Retained acceptance model:** `1.7.0-dev.39`  
**Evidence type:** `device` only  
**Authority boundary:** This procedure records physical-device observations; it does not itself grant acceptance, lifecycle authority, or any Human, Performance, Energy, or Assistive Technology evidence.

## Purpose

This procedure defines how real physical-device observations may be recorded for the retained V1.7.1 qualification matrix. It exists because browser CI, screenshots, responsive viewport emulation, Android emulators, Apple simulators, synthetic fixtures, and source-level validators cannot establish that Glaze behavior was actually observed on the claimed physical form factor or native platform.

The machine-readable control is `contracts/v1.7/qualification.v1.2.device.plan.json`. Start each real candidate record from `acceptance/v1.7.1-device-evidence.template.json`; never edit the canonical template into evidence. Validate records with `scripts/validate_glaze_v1_7_1_device_qualification.py`.

Use `scripts/prepare_glaze_v1_7_1_device_qualification.py` to create an exact-source review package containing the frozen source contracts, current protocol files, and a source/tooling manifest. The package is a provenance aid only; it is not device evidence.

## Eligible device evidence groups

After separate governed review, one exact-source physical-device record may contribute the **device** evidence group to exactly one of these retained lanes:

- `mobile` — still also requires its retained `rendered` group.
- `tablet` — still also requires its retained `rendered` group.
- `desktop` — still also requires its retained `rendered` group.
- `foldable` — still also requires its retained `rendered` group.
- `tv` — still also requires its retained `rendered` group.
- `wearable` — conditional where claimed; still also requires its retained `rendered` group.
- `touch` — still separately requires `human` evidence.
- `native-behavior` — still separately requires `human` evidence.
- `energy-behavior` — conditional where applicable; this record can supply only its `device` group and **never** its separate `energy` group.

A session pass does not automatically close any lane. The retained acceptance matrix and governed review process remain authoritative for combining evidence groups.

## Physical-device boundary

Every candidate record must represent a real physical device:

- `physicalDevice: true`;
- `emulator: false`;
- concrete manufacturer, model, architecture, platform version/build, and display refresh rate;
- no serial number, account identifier, credential, private content, or unrelated user data;
- a real human operator must execute the session;
- the exact Glaze source revision and exact review tooling revision must be recorded;
- the actual integration/application build under test must be identified independently.

An emulator or simulator may support development, debugging, or preflight checks, but it cannot be recorded as `device` evidence.

One device never implies qualification of another form factor, OEM, platform family, native toolkit, or support matrix.

## Integration identity

Physical-device behavior occurs through an implementation using Glaze, not merely by inspecting source files. Every candidate record therefore identifies:

- application/integration name;
- GoreeCloud integration repository;
- exact 40-character integration revision;
- build identifier;
- implementation kind;
- the Glaze source revision integrated by that build.

The integrated Glaze revision must be exactly `4b9d085a5177b96cc31d4270b38d792a59872e37`.

For `native-behavior`, the implementation must be one of:

- `android-compose`;
- `apple-swiftui`;
- `linux-native`; or
- an explicitly named `other-native` implementation.

A browser/web implementation may support form-factor or Touch device observation, but it cannot satisfy the Native behavior device group.

## Common scenario matrix

Every record covers these six scenarios:

1. `source-and-build-identity` — verify the running build and record identify the exact integration revision and frozen Glaze revision.
2. `physical-device-and-form-factor` — verify the observed hardware is physical and the claimed form factor matches the device being used.
3. `platform-insets-and-safe-areas` — verify platform-owned safe areas/insets are respected and no hard-coded cutout assumption causes content loss.
4. `task-and-state-continuity` — verify layout/input/environment changes do not reset task, navigation, focus, selection, draft, or authoritative state unexpectedly.
5. `accessibility-preference-precedence` — verify applicable system accessibility preferences take precedence over optional visual/motion richness without changing truth.
6. `semantic-authority-preservation` — verify form-factor/input/native adaptation does not manufacture provider state, permission, authorization, capability, or result truth.

Each targeted lane adds exactly one lane-specific scenario.

## Lane-specific requirements

### Mobile — `mobile-navigation-and-reachability`

Use a physical mobile device with `formFactor: mobile`. Observe compact/bottom navigation as applicable, reachable primary actions, single-primary-task hierarchy, touch-floor targets, platform safe areas, and sheet/full-screen overlays without relying on width alone as profile authority.

### Tablet — `tablet-dual-pane-and-mixed-input`

Use a physical tablet with `formFactor: tablet`. Observe dual-pane/supporting layout behavior, touch-and-pointer-aware reachability where hardware permits, rail/compact-sidebar navigation, platform safe areas, and continuity across available input changes.

### Desktop — `desktop-windowing-and-mixed-input`

Use physical desktop/laptop-class hardware with `formFactor: desktop`. Observe platform windowing/insets, multi-region composition, stable toolbar/contextual action placement, pointer/keyboard behavior, and touch/stylus only where actually available.

### Foldable — `foldable-posture-and-unsafe-regions`

Use a physical foldable device with `formFactor: foldable`. The record must include both `folded` and `unfolded` in `posturesObserved`. Observe posture-aware composition, task continuity, and avoidance of hinge/unsafe regions.

### TV — `tv-far-view-and-directional-focus`

Use a physical TV/TV-device configuration with `formFactor: tv`. The actual input used must include `remote-dpad`. Observe directional focus, visible focus order, far-view typography/hierarchy, platform safe region, and task-dependent large-region presentation.

### Wearable — `wearable-glanceability-and-rotary-or-touch`

Use a physical wearable with `formFactor: wearable`. The actual input used must include at least one of `touch` or `rotary`. Observe glanceable hierarchy, shallow navigation, platform insets, minimal motion, and the platform's actual interaction path. Wearable applicability remains governed separately; this protocol does not decide whether the lane is applicable.

### Touch — `real-touch-and-semantic-alternatives`

Use real touch hardware and include `touch` in `actualInputsUsed`. Observe direct activation plus semantic alternatives for any operation that would otherwise depend on drag, swipe, hover, long press, precision pointing, or multi-touch. This supplies only Device evidence; separate Human evidence remains required.

### Native behavior — `native-toolkit-and-platform-conventions`

Use a physical device running a native implementation. Record the actual native toolkit. Observe native interaction behavior, system motion/accessibility preference bridging, native rendering/windowing conventions, platform capability ownership, final-state correctness, and semantic consistency without requiring pixel-identical or timing-identical behavior across platforms. Separate Human evidence remains required.

### Energy behavior — `background-offscreen-device-lifecycle`

Use a physical device and record power source, battery percentage, thermal state before/after, and controlled background-load context. Observe background/off-screen lifecycle behavior and whether optional visual work suspends where the application/platform exposes that behavior. **Do not infer power draw, thermal acceptance, battery efficiency, or Energy evidence from this record.** Independent `energy` evidence remains required.

## Scenario decisions

Every required scenario is either:

- `pass` — the stated observation was actually performed and no blocking finding was observed for this device session; or
- `fail` — the observation exposed a blocking issue or could not be completed as required.

A `session-pass` requires every required common and lane-specific scenario to pass. A `session-fail` is required when any scenario fails.

A session pass is still only candidate Device evidence until separate governed review accepts it.

## Validation

Validate protocol/source boundaries and synthetic negative cases:

```bash
python scripts/validate_glaze_v1_7_1_device_qualification.py --self-test
```

Prepare an exact-source review package:

```bash
python scripts/prepare_glaze_v1_7_1_device_qualification.py --out _v171-device-review
```

Validate a completed real record:

```bash
python scripts/validate_glaze_v1_7_1_device_qualification.py --record /path/to/device-session.json
```

The self-test uses synthetic records only. It deliberately rejects stale Glaze revisions, emulators represented as physical devices, mismatched form factors, missing Touch hardware, missing foldable postures, TV records without real directional input, web implementations represented as Native behavior, and Energy behavior records that omit device power/thermal context.

## Completion boundary

This control tranche is complete when the plan, schema, fail-closed template, procedure, exact-source review-package helper, validator, repository documentation, and CI self-tests are exact-head green.

**Physical-device acceptance remains incomplete** until applicable real sessions are executed on actual claimed devices, validated, independently reviewed, and governed into durable exact-source evidence. Human, Assistive Technology, Performance, Energy, Section 48, V1.7.1 lifecycle, consumer, deployment, publication, and production acceptance remain separate.

Glaze V1.7 / `1.7.0` remains the bounded Stable/Anchor release throughout this work.

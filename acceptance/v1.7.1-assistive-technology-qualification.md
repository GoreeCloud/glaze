# Glaze V1.7.1 — Manual Assistive-Technology Qualification

**Lifecycle:** V1.7.1 Development qualification control only
**Current Stable baseline:** Glaze V1.7 / `1.7.0`
**Frozen source under review:** `4b9d085a5177b96cc31d4270b38d792a59872e37` / `1.7.0-dev.47`
**Retained acceptance model:** `1.7.0-dev.39`
**Authority boundary:** This procedure records real human-operated assistive-technology sessions; it does not itself grant acceptance or promotion.

## Purpose

This procedure defines how real assistive-technology sessions are recorded against the frozen V1.7 Development source retained by V1.7.1. It exists because machine semantics, browser accessibility trees, automated keyboard traversal, rendered screenshots, and CI cannot establish how TalkBack, Voice Access, Switch Access, VoiceOver, Switch Control, Orca, Narrator, or another claimed assistive technology behaves for a person on real hardware.

The machine-readable control is `contracts/v1.7/qualification.v1.2.assistive-technology.plan.json`. Start every real session record from `acceptance/v1.7.1-assistive-technology-evidence.template.json`; never mutate the canonical template into evidence. Validate records with `scripts/validate_glaze_v1_7_1_assistive_technology_qualification.py`.

The local review surface is `reference/v1.7/assistive-technology-qualification.html`. Prepare an exact-source review root with `scripts/prepare_glaze_v1_7_1_assistive_technology_qualification.py`.

## What this evidence can and cannot satisfy

After separate governed review, a valid exact-source session may contribute the **assistive-technology** evidence group to:

- `assistive-technology`; and
- `alternative-input`, whose separate **human** evidence group still remains required.

A passing session does **not** automatically close either lane. It also does not establish Human evidence, Device evidence, complete native-platform accessibility parity, Section 41 or Section 48 acceptance, V1.7.1 lifecycle promotion, consumer eligibility, deployment, publication, or production acceptance.

## Exact-source and human-operation requirements

Every real session must:

- use the prepared review root for exact source `4b9d085a5177b96cc31d4270b38d792a59872e37`;
- record the exact tooling revision used to prepare the review surface;
- identify repository `GoreeCloud/glaze`;
- identify the human operator/reviewer;
- set `manualExecution: true` only after a real human-operated session;
- identify the platform, physical device manufacturer/model, OS version/build, assistive-technology name/version, and input mode;
- use a physical device for the recorded session (`physicalDevice: true`, `emulator: false`);
- record scenario-level pass/fail/not-applicable-with-reason outcomes and concrete observations;
- record a defect/finding for every failed scenario;
- keep evidence free of credentials, private content, provider secrets, and unrelated user data.

Moving aliases, abbreviated SHAs, copied observations from another revision, placeholders such as TBD/unknown, machine-only execution represented as manual evidence, and emulator-only sessions represented as physical sessions are prohibited.

## Recognized assistive technologies

The control recognizes:

- TalkBack
- Voice Access
- Switch Access
- VoiceOver
- Switch Control
- Orca
- Narrator
- another explicitly named technology through `Other`

The actual supported/claimed platform matrix governs what must be tested. One session never implies acceptance for another technology, platform, input model, or device class.

## Required scenario matrix

Every session record covers exactly these scenarios:

1. `source-and-orientation` — verify the review surface identifies the exact source and the technology can orient the operator to page purpose and boundaries.
2. `navigate-semantic-regions` — navigate header, review instructions, test controls, status/error regions, and task-continuity region in a predictable order.
3. `activate-semantic-actions` — activate the primary controls through the assistive technology without requiring an inaccessible pointer-only gesture.
4. `focus-order-and-reachability` — verify meaningful focus/virtual-cursor order and reachability of controls and recovery actions.
5. `names-roles-states-and-values` — confirm controls expose useful accessible names, roles, current states, values, and disabled/expanded/checked semantics.
6. `dynamic-status-and-recovery-announcement` — verify progress/status changes and the example validation error/recovery path are announced or otherwise presented appropriately.
7. `large-text-200-percent` — verify 200% text/zoom preserves reflow, control reachability, task state, and understandable ordering.
8. `reduced-transparency-and-forced-colors` — verify applicable platform/browser accessibility presentation preserves meaning, focus, and control visibility.
9. `switch-voice-alternative-paths` — where applicable, verify a semantic alternative exists for operations that could otherwise depend on drag, hover, precision pointing, or another unsuitable physical technique.
10. `task-continuity-across-input-change` — verify draft/task state survives the review surface's controlled input/layout transition and focus can be logically restored.

## Observation dimensions

Record what was actually spoken, exposed, focused, activated, announced, or blocked. Observations should cover:

- spoken/presented name;
- role, state, and value;
- reading and focus order;
- action reachability;
- dynamic-state announcement;
- error and recovery feedback;
- 200% large-text reflow and reachability;
- accessibility-preference precedence over optional visual richness;
- alternative input path;
- task and focus continuity.

For voice or switch technologies, record the actual command, switch path, scanning behavior, or semantic target used.

## Session decision meanings

- `session-pass` — the required scenarios in this one session contain no failed scenario.
- `session-fail` — one or more required scenarios have a blocking/manual finding.

A single passing session is evidence for only that exact source/platform/device/technology combination and remains a candidate record until governed review accepts it.

## Validation

Validate the protocol and synthetic negative cases:

```bash
python scripts/validate_glaze_v1_7_1_assistive_technology_qualification.py --self-test
```

Prepare the exact-source review root:

```bash
python scripts/prepare_glaze_v1_7_1_assistive_technology_qualification.py --out _v171-at-review
python -m http.server 8766 --bind 127.0.0.1 --directory _v171-at-review
```

Then open:

```text
http://127.0.0.1:8766/reference/v1.7/assistive-technology-qualification.html
```

Validate a completed real session record:

```bash
python scripts/validate_glaze_v1_7_1_assistive_technology_qualification.py --record /path/to/session.json
```

The validator self-test is synthetic format testing only. It is never a screen-reader, voice-access, switch-access, human, device, or lifecycle acceptance result.

## Completion boundary

This control tranche is complete when the plan, fail-closed template, validator, exact-source preparer, review surface, documentation, and CI self-tests are exact-head green. The **Assistive technology** lane remains unverified until applicable real sessions are executed by people, validated, reviewed, and governed into durable exact-source evidence. **Alternative input** additionally requires its independent Human evidence group.

Glaze V1.7 / `1.7.0` remains the bounded Stable/Anchor release throughout this work.

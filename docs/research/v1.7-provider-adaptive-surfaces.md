# Glaze UI V1.7 dev.41 — Provider Adaptive Surfaces Reforge Research

**Research date:** 2026-09-30  
**Scope:** Glaze Contextual Actions, Glaze Brief, and Glaze Control Center.

## Projects and standards reviewed

### GLib / GIO GAction
- Project: GLib / GIO.
- License: LGPL-2.1-or-later.
- Primary references: GIO Action and ActionGroup API documentation.
- Relevant finding: action identity, enabled state, optional state, and activation are modeled explicitly; disabled actions cannot be activated externally.
- GoreeCloud requirement extracted: presentation of an action must remain separate from provider-owned availability/state and from the system that actually performs execution.

### GNOME Shell
- Project: GNOME Shell.
- License: GPL-2.0-or-later.
- Primary references: Shell.ActionMode and Shell namespace API documentation.
- Relevant finding: actions such as keybindings and gestures are scoped to explicit shell states/modes.
- GoreeCloud requirement extracted: contextual actions must be scoped to authoritative context rather than assumed globally available.

### Material Web
- Project: Material Web.
- License: Apache-2.0.
- Primary references: Material Web menu documentation and repository metadata.
- Relevant finding: temporary action-choice surfaces distinguish menu roles, disabled/non-interactive state, keyboard navigation, selection, and close behavior.
- GoreeCloud requirement extracted: contextual action presentation must expose semantic interaction state and keyboard access without converting presentation into provider authority.

### Fluent UI
- Project: Fluent UI.
- License: MIT for the Fluent UI React repository; referenced fonts/icons have separate asset terms.
- Primary references: Fluent UI repository README and LICENSE.
- Relevant finding: a reusable design system can expose shared action/control primitives while keeping application behavior outside the visual component itself.
- GoreeCloud requirement extracted: Glaze should provide reusable semantic action/control presentation without importing another system's product identity, assets, implementation, or raw visual constants.

### W3C WAI-ARIA Authoring Practices
- Standard/practice source: W3C WAI-ARIA APG.
- Primary references: Menu Button, Menu and Menubar, Button, Feed, and Keyboard Interface patterns/practices.
- Relevant findings: interactive roles must match behavior; disabled items remain semantically understandable; keyboard focus movement must be predictable; menu dismissal commonly returns focus to the invoking context; feed/article structure must preserve readable order.
- GoreeCloud requirement extracted: Contextual Actions, Brief, and Control Center must preserve semantic roles, visible/predictable focus, keyboard-equivalent access, reading order, and non-color/non-motion meaning.

## Reforge boundary

The external projects and standards above were used to understand interaction patterns, accessibility expectations, and action/state separation.

No third-party component implementation, source structure, token value, animation value, visual identity, asset, font, icon, or product-specific composition is incorporated by dev.41.

No mechanical rewriting or line-by-line translation was performed.

The dev.41 implementation is an original GoreeCloud semantic presentation resolver that composes existing Glaze UI authority, accessibility, continuity, expression, and performance foundations.

## GoreeCloud-specific improvements

The dev.41 design adds GoreeCloud-specific fail-closed boundaries:

- provider identity must be authoritative before a provider-owned item is eligible for presentation;
- contextual action availability must be authoritative before the action is actionable;
- destructive presentation cannot be asserted from an untrusted visual-role request;
- action ranking and provider precedence are never invented by Glaze;
- Glaze Brief personalization cannot suppress authoritative required/critical communication;
- control availability, state, policy, permission, authorization, execution, and result truth remain outside Glaze authority;
- explicit user intent produces only a proposal for the responsible system, never automatic execution;
- personalization may change expression but must not change truth.

## Acceptance boundary

This research and source tranche do not establish rendered, native-platform, assistive-technology, representative-device, keyboard/switch/voice, performance, energy, privacy/security-provider integration, or human visual acceptance.

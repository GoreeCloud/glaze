# GLAZE UI V1.7 — Accessibility Continuity Research Record

Status: Development research provenance  
Bounded target: V1.7 v1.2 Section 41  
Implementation target: 1.7.0-dev.34  
Stable baseline: GLAZE UI V1.6 / 1.6.0  
Research date: 2026-09-27

## Purpose

This record captures external accessibility and focus-continuity research used to derive bounded Section 41 requirements. It is research provenance, not acceptance evidence. GoreeCloud source is independently designed under the Reforge process.

The governing GoreeCloud requirements remain the V1.7 Section 41 plan plus the current Glaze UI Design Language, Glaze UI Application Conformance policy, Glaze Motion standard, and System-Wide Motion Continuity and Performance standard. External projects are used only to extract architectural lessons.

## Sources reviewed

### W3C ARIA Authoring Practices

- Repository: `w3c/aria-practices`
- Exact revision: `3f094fde1c81b25dfa69162563bf28d093f854d4`
- License: W3C Software and Document License.
- Material reviewed: `content/practices/keyboard-interface/keyboard-interface-practice.html` and repository license at the exact revision.
- Requirement lesson: keyboard interfaces require discernible, persistent, predictable focus; when the active element disappears, focus should move logically rather than collapse to an unusable document state. Focus and selection remain distinct concepts, and standard semantic/keyboard conventions support screen-reader and voice users.
- GoreeCloud decision: Accessibility Continuity preserves current focus identity through task state where possible; when the current focus target is authoritatively unavailable, the layer may expose a caller-authoritative logical fallback proposal but never executes focus itself. Keyboard focus remains visible and distinct from selection.

### Adobe React Spectrum / React Aria

- Repository: `adobe/react-spectrum`
- Exact revision: `16eead67e83cf42f3c0ee46ef6eb7a2032778378`
- License: Apache-2.0.
- Material reviewed: `packages/react-aria/src/focus/FocusScope.tsx` at the exact revision.
- Requirement lesson: focus scope architecture benefits from explicit containment, restoration of previously focused elements, and programmatic focus-management boundaries rather than relying on incidental DOM order after dynamic UI changes.
- GoreeCloud decision: Section 41 treats focus continuity as governed state preservation and exposes restoration proposals only when caller/platform truth says the previous target is unavailable. Focus execution remains owned by the application/platform.

### AndroidX Compose UI

- Repository: `androidx/androidx`
- Exact revision: `23327507f7fc7d5b19d65fec4b090f60c970079b`
- License: Apache-2.0.
- Material reviewed: `compose/ui/ui/src/commonMain/kotlin/androidx/compose/ui/focus/FocusRestorer.kt` and exact-revision accessibility/semantics references.
- Requirement lesson: focus restoration can retain a previously focused child across composition/configuration changes and use an explicit fallback when the original target can no longer be focused.
- GoreeCloud decision: Accessibility-driven recomposition must preserve task and focus identity where technically possible. A fallback target is accepted only when supplied and validated by an authoritative caller; Glaze never invents or executes focus targets.

## GoreeCloud-native Section 41 decisions

The bounded dev.34 layer:

- Covers exactly the planned accessibility changes: Large text, Reduced Motion, Reduced Transparency, Increased Contrast, Forced Colors, screen readers, switch access, voice access, Touch Assistance, and keyboard navigation.
- Uses the existing V1.7 Task Continuity `accessibility-mode` environment change so navigation destination, focus identity, selection, scroll position, expanded regions, drafts, form state, filters/queries, pane state, pending interactions, media state, and working context remain governed by the same continuity model.
- Lets authoritative Large Text context simplify/recompose adaptive presentation while semantic surface identity and current task state remain intact.
- Preserves the current V1.6 accessibility-profile semantics for reflow, reduced transparency, increased contrast, strong focus, Touch Assistance, and screen-reader-aware presentation without treating those historical Development modules as current release authority.
- Uses V1.6 focus/motion semantics for visible focus, focus-vs-selection distinction, and logical restoration proposals without allowing Glaze to execute focus.
- Uses V1.7 Adaptive Input for authoritative transitions to keyboard, switch, voice, touch, or assistive input models. Accessibility expectations alone do not create input-model truth.
- Uses V1.7 Motion Expression Profiles and Reduced Motion Equivalents so authoritative Reduced Motion caps optional richness and preserves direct manipulation while never rewriting the selected durable motion preference.
- Requires opaque/solid equivalents for Reduced Transparency, higher-contrast alternatives for Increased Contrast, and platform palette authority plus non-color-only meaning in Forced Colors.
- Requires semantic structure, accessible names/roles, predictable reading order, and focus continuity for screen-reader use without manufacturing announcements or assistive-technology truth.
- Keeps physical gestures/bindings from becoming semantic-action authority for switch, voice, Touch Assistance, or keyboard navigation.
- Rejects raw font sizes, text-scale percentages, contrast ratios, raw target sizes, raw animation values, performance measurements, assistive-technology transcripts/evidence payloads, scores, ratings, or caller-injected acceptance conclusions.
- Does not persist accessibility preferences, change provider/application truth, grant permission/authorization, execute navigation/actions/focus, grant acceptance, or promote lifecycle state.

## Current GoreeCloud governance alignment

Current Stable governance requires accessibility to be part of Glaze UI itself, including visible focus, keyboard access, Reduced Motion, Reduced Transparency, Increased Contrast, Forced Colors, large/200% text behavior, predictable reading/focus order, non-color-only meaning, and applicable assistive-technology support. Accessibility constraints outrank visual richness. Motion governance additionally requires focus, reading order, screen-reader semantics, switch behavior, and other supported assistive interaction models to remain correct during and after transitions.

dev.34 encodes those requirements as Development source semantics only. It does not convert Stable governance text into new V1.7 acceptance evidence.

## Security and privacy review

Accessibility state is treated as caller/platform-owned context. Non-neutral accessibility changes are applied only when `accessibilityStateAuthoritative` is explicit; otherwise they fail closed and current task state is still preserved. The layer does not infer accessibility needs from private content, telemetry, behavior profiling, or provider data. Raw assistive-technology transcripts and acceptance evidence are outside the runtime contract.

## Incorporation statement

No third-party source code, UI implementation, focus-management implementation, algorithms, components, raw presentation values, assets, icons, fonts, visual identity, trademarks, or branding are incorporated by this research. The external sources were used to extract requirements and architectural lessons only.

## Validation boundary

Successful accessibility behavior in the researched projects is not evidence for Glaze UI. dev.34 must pass its own exact-revision validator, retained V1.7 and V1.6 regressions, V1.6 Anchor-preservation/security gates, and later representative rendered/native/large-text/Forced-Colors/screen-reader/switch/voice/Touch-Assistance/keyboard/performance/energy/human accessibility acceptance before Section 41 can be considered complete.

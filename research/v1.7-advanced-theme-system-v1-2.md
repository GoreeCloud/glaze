## GoreeCloud requirements derived from research

1. Keep Advanced Theme Manager inputs semantic and bounded rather than exposing arbitrary implementation tokens.
2. Generate palettes locally from authoritative supplied seeds and re-run accessibility validation after derivation.
3. Keep protected semantic palettes outside user-theme authority.
4. Distinguish navigation, system truth, connectivity, synchronization, and data-visualization color domains.
5. Require a declarative, inspectible, non-executable theme-package format with no remote runtime resources.
6. Keep theme history, per-application preferences, and per-device preferences caller-owned; Glaze proposes presentation state but does not persist it.
7. Fail unsafe themes to a known-good presentation while keeping Theme Manager repair/reset access reachable.
8. Keep color as a reinforcing cue; every meaningful state requires a non-color equivalent.

## Independent reimplementation boundary

No third-party source code, algorithms, exact palette constants, token names, visual layouts, assets, icons, fonts, animation values, or product identity are copied into Glaze UI by this tranche. The reviewed projects are used only to identify general design-system problems and requirements. The implementation remains original GoreeCloud code under GoreeCloud's existing repository license and governance.

This record does not establish license compatibility for future direct source adoption because no source is adopted here. It does not establish V1.7 acceptance, consumer eligibility, Release Candidate or Anchor promotion, deployment, or production acceptance.
